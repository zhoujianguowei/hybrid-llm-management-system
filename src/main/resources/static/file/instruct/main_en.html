System Overview

This system (Hybrid LLM Management System) is a comprehensive management platform for locally deployed large language models, integrating file management, user permissions, model scheduling, AI conversation, and system monitoring into one secure, efficient, and convenient all-in-one experience.

Built on Java + Spring Boot, the frontend uses Bootstrap 5, and the backend schedules local GGUF-format large language models through llama.cpp, while also supporting OpenAI-compatible remote API integration. Its core objective is to address the cumbersome path permission management, model parameter configuration, and resource monitoring challenges in local model deployment.

The system is available in two editions, identified by the following version suffixes:

EditionVersion SuffixDescriptionIncluded Features
Base Editionrelease_baseStreamlined deployment versionCore features: file management, user management, AI chat, permission system, etc.
Ultimate Editionrelease_ultimateFull-featured versionAll Base Edition features + model management, resource monitoring, scheduled power control, and other advanced features
Multimodal Capability Notice: The current version's multimodal capabilities only support images; audio and video input are not supported.
Compatibility Notice: The scheduled shutdown/restart feature depends on the underlying OS instruction set and hardware support; not all machine models can operate normally. Current test system status: Dual X99 (Ubuntu 22.04, E5-2696 v4) and Mac M1 Pro shutdown/restart work normally; Windows 10 64-bit (z690 motherboard, i7-13700K) shutdown works normally, but automatic wake-up restart is limited by motherboard BIOS and cannot wake up in self-tests.
GPU Monitoring Notice: GPU monitoring relies on the nvidia-smi tool and only supports systems with NVIDIA GPUs. macOS uses Apple Silicon (M series) or integrated graphics, which lack corresponding monitoring interfaces, so GPU monitoring panels are not available on macOS.

Core Features

Fully Offline, No Internet Required

Frontend resources are fully offline, with no dependency on external CDNs. Ready to use out of the box, convenient for intranet deployment.

No Database Configuration, Cross-Platform

Supports Windows, Linux, and macOS platforms with no database configuration needed. Single JAR deployment, zero dependencies, ready to run upon startup.

Fine-Grained Path Permissions

Path-inheritance-based permission verification mechanism supporting five permission types: read, execute, upload, download, and delete. Supports role-based minimum permission restrictions and additional authorization for specific users to ensure data security.

Project-Level AI Analysis

Supports batch file upload with automatic text content extraction. Submit key files from an entire source directory to AI at once for cross-file project-level code analysis and refactoring suggestions.

Latest llama.cpp Feature Support

Deeply integrated with the latest llama.cpp capabilities, fully supporting multi-GPU parallel acceleration (SM Tensor in llama.cpp) and Speculative Decoding (predictive inference) acceleration: supports MTP (Multi-Token Prediction), DFlash and DSpark types, significantly improving large model inference throughput and response speed.

Automated GGUF Management

Automatically identifies GGUF shard files with one-click merge support. Built-in naming convention checks ensure consistent model file naming for quick retrieval and scheduling.

Real-Time Resource Monitoring

Integrated nvidia-smi real-time monitoring with trend charts for GPU memory usage and system memory, helping administrators assess resource availability before launching models.

Smart Scheduled Restart

Supports one-time and recurring (by workday) scheduled shutdown/wake tasks. Features task conflict detection and pre-expiration warnings, suitable for unattended server environments.

Fine-Grained Permission System

This system uses a path-inheritance-based permission verification algorithm to ensure absolute security of resource access.

Permission Verification Logic

  • Path InheritanceWhen accessing /home/data/file.txt, if no rule is set for this file, the system traces upward to /home/data → /home → / until the nearest matching rule is found.
  • Permission Cascade (Priority)Permissions have an inclusion relationship; higher levels automatically grant lower-level permissions. Priority order:
    Delete > Upload > Download > Execute > Read.
    For example, a user with "Delete" permission automatically has all other permissions for that path.
  • Role & User Dual VerificationEach permission can configure a "minimum allowed role" (e.g., regular users and above), and also supports adding a "specific authorized users" list for flexible privilege management.

Permission Types & Functions Explained

The system categorizes permissions into "general permissions" and "folder-specific permissions" as follows:

Permission NameApplies ToDetailed Description
ReadFile / Folder[Lowest Permission] Allows viewing file content and previewing files. For folders, it only means the folder is visible in the list, cannot enter the folder to view its contents.
ExecuteFolder OnlyAllows users to "enter" the directory; a prerequisite for viewing directory listings and accessing sub-items.
DownloadFile / FolderAllows downloading individual files or packaging entire folders for download.
UploadFolder OnlyAllows uploading new files to or overwriting existing files in the directory.
DeleteFile / Folder[Highest Permission] Allows deleting the file or recursively deleting the entire folder.
Special Mechanism: Path Penetration
The system supports permission verification based on the final target. If a user lacks "Execute" permission for a parent directory but has "Read" permission for a deeply nested sub-file (e.g., has read permission for /home/nice/good.txt but no execute permission for /home/nice), the user can still directly access that file. In this case, while browsing, the user can only see the path leading to that file (e.g., only /home/nice is visible) and cannot see other files in the parent directory (such as /home).

Permission Configuration

Administrators can define rules for any path through "Permission Settings".

Verification Constraints: To prevent permission configuration conflicts, the system requires that the role scope for higher permissions must be a subset of the role scope for lower permissions (e.g., those allowed to delete must also be allowed to read).

Permission Tree Management

Through a visual tree structure, administrators can intuitively view the permission distribution across the entire system and quickly locate and modify permissions for specific subdirectories.

Path Protection Mechanism

After checking "Protected" in the permission edit interface, the path will be locked. Protected paths display a special indicator in the file management interface, and all deletion requests will be directly blocked.

Model Function Definition & Thinking Mode Configuration

The model function definition assigns multimodal capabilities (image/video/audio), thinking mode, and visibility to models matching specific names, via exact match or regular expressions. For models that support "deep thinking" (reasoning) capabilities, thinking modes can be flexibly configured here; the Override Auto-Detection option forces this entry to override the configuration auto-detected by the system (see below).

Auto-Detection from GGUF Metadata

When launching a local GGUF model, the system automatically parses the model's tokenizer.chat_template metadata to detect thinking-related parameters. If the chat template contains keywords like thinking_mode, enable_thinking, thinking, or reasoning_effort, the system automatically populates the thinking mode configuration, eliminating manual setup.

Auto-Detection Logic: The system scans the GGUF file's chat template for recognized parameter keywords and thinking level values (e.g., thinking_mode three-state values disabled / adaptive / enabled, and reasoning_effort level values like no_think, low, high, max). Detection priority: thinking_mode > other parameter combinations. Based on the detected parameters, it determines the appropriate thinking mode and available levels.

Thinking Modes

The system supports four thinking modes, each suited to different model capabilities:

ModeParameters UsedDescriptionApplicable Models
Single Thinking Modeenable_thinking / thinkingUses a single boolean parameter (enable_thinking or thinking) to control the on/off state of thinking (true / false), with no intensity levels.Models whose chat template uses a boolean thinking param, such as Qwen3.5 and Qwen3.6 series
Multi-Stage Thinking Modereasoning_effortUses reasoning_effort to control both the on/off state and intensity of thinking. The parameter value range includes an off level (no_think) and intensity levels (low, medium, high, xhigh, max), and at least one intensity level must be selected.Models that use reasoning_effort to control thinking, such as hy3 series
Hybrid Modeenable_thinking / thinking + reasoning_effortUses two parameters simultaneously: a boolean parameter (enable_thinking or thinking) controls the on/off state, while reasoning_effort controls thinking intensity. When an off level is selected, only the boolean parameter is sent; when an intensity level is selected, both parameters are sent.Models requiring separate on/off and intensity control, such as Qwen3.8 series and DeepSeek V4 Flash
Thinking Mode (thinking_mode)thinking_modeUses a single parameter to control the thinking mode, supporting three states: disabled (disable thinking), adaptive (adaptive, model decides whether to think), and enabled (force enable thinking). This mode has the highest detection priority in GGUF metadata.Models with native thinking_mode parameter support, such as MiniMax M3
Default Level Difference: The default selection logic for thinking_mode differs from other modes. In the model launch configuration page, thinking_mode defaults to the highest level (e.g., enabled) to maximize thinking capability at startup. In the chat page, it defaults to the lowest level (e.g., disabled) for faster response times in everyday conversations.

Override Auto-Detection

Locally launched models are auto-detected by the system with their actual features and thinking configuration (derived from launch parameters and GGUF chat template parsing). The "Override Auto-Detection" option in the model function definition determines which one wins on conflict:

"Override Auto-Detection" is unchecked by default: when checked, the multimodal features and thinking configuration in this entry forcibly override the auto-detected model configuration (if thinking mode is set to "Not Supported", the auto-detected thinking configuration is cleared as well); when unchecked, auto-detected local models keep their detected values, and only the visibility setting of this entry takes effect.
  • Auto-detected models (llama.cpp models launched locally by the system): with this option unchecked, the detected values win; when checked, this config entry wins.
  • Models scanned via OpenAPI integration: no auto-detected info exists, so the model function definition always applies; this option has no effect on them.
  • Visibility: always applies regardless of this option.
Configuration Scope: Thinking mode configuration is matched to models via exact name match or regular expressions. A configuration only takes effect for matching models. Unmatched models will not have thinking mode enabled.

Main Model File Naming Convention

Main model files must follow a unified naming format for automatic system recognition and matching:

RuleDescription
FormatModelName_QuantizationType.gguf
SeparatorModel name and quantization type are connected with an underscore _
Base NameThe part before the first underscore is considered the model base name, used for matching mmproj and MTP files
Exampleqwen3.6_Q5_1.gguf → Base name qwen3.6, quantization type Q5_1
Important Limitation: The model name portion cannot contain underscores (_). The system uses the first underscore as a separator to distinguish between the model name and quantization type. If the model name itself contains an underscore, the system will incorrectly truncate it, causing the model to be unrecognized. For example: qwen_3.6_Q5_1.gguf would be parsed as base name qwen, quantization type 3.6_Q5_1, which is incorrect.

Multimodal File (mmproj) Naming Convention

mmproj files are used for vision-language multimodal models and must be placed in the mmproj/ subdirectory under the model directory. Filenames must start with mmproj-; the system will automatically match based on the main model filename:

PriorityMatching RuleExample
Priority 1Full Name Matchmmproj/mmproj-qwen3.6_Q5_1.gguf
Priority 2Base Name + Precision Suffix Match
mmproj/mmproj-{base name}-{precision}.gguf		mmproj/mmproj-qwen3.6-f32.gguf
mmproj/mmproj-qwen3.6-bf16.gguf etc.
Priority 3Base Name Fallback Matchmmproj/mmproj-qwen3.6.gguf
Precision suffix is case-insensitive (e.g., F32 / f32 are both recognized). Supported precision suffixes include: F32, BF16, F16, Q8_0.

MTP Draft Model File Naming Convention

MTP (Multi-Token Prediction) is llama.cpp's multi-token prediction acceleration feature. If the main model file itself already contains MTP layers, no separate draft model file is needed; only when the main model does not contain MTP layers must the draft model be placed in the mtp/ subdirectory under the model directory, with filenames starting with mtp-:

PriorityMatching RuleExample
Priority 1Base Name + Precision Suffix Match
mtp/mtp-{base name}-{precision}.gguf		mtp/mtp-qwen3.6-f32.gguf
mtp/mtp-qwen3.6-bf16.gguf etc.
Priority 2Base Name Fallback Matchmtp/mtp-qwen3.6.gguf
Select the MTP type in "Speculative Decoding" when launching a model to enable MTP acceleration: it takes effect directly when the main model file has built-in MTP layers, with no extra configuration needed; otherwise the system automatically detects and loads the corresponding draft model from the mtp/ subdirectory. DFlash/DSpark types require a manual path to a separate draft model file.

GGUF Shard Merging

Large models downloaded may be split into multiple shard files (e.g., model-00001-of-00002.gguf). The system provides automatic recognition and one-click merge functionality:

  • Auto DetectionClick the "Model Naming & Shard Merging" button; the system automatically scans for shard files in the model directory
  • One-Click MergeClick the "One-Click Rename" button; the system will automatically merge shards and delete original shard files

Note: Merge operations will delete original shard files; ensure backups are made.

Launch Configuration & Underlying Parameter Mapping

Fine-grained parameter tuning can be performed before launching a model. The system converts UI configuration into llama.cpp command-line parameters for high-performance inference.

1. Text Sampling Parameters (Control "What to Say")

These parameters directly affect the probability distribution (Logits) when the model outputs the next Token, determining the creativity, diversity, and coherence of generated text.

UI ConfigurationUnderlying ParameterDetailed Description
Temperature--tempControls generation randomness by scaling Logits at the Softmax layer:
• Lower values (e.g., 0.2) make the model favor the highest-probability words, producing stable but rigid output
• Higher values (e.g., 0.8-1.2) flatten the distribution, producing more creative output but potentially causing hallucinations
• Setting to 0 enables Greedy Decoding, always choosing the highest-probability word
Range: 0.00-2.00, Default: 0.80
Top K--top-kAbsolute count truncation. When predicting the next word, only keep the top K most probable tokens and discard all others:
• Setting to 40 means the model only samples from the 40 most likely words
• Effectively prevents the model from generating extremely unlikely "long-tail gibberish" at high temperatures
• Setting to -1 fully disables this feature (equivalent to vocab size)
Range: -1-1024, Default: 40
Top P--top-pCumulative probability truncation (Nucleus Sampling). Sort candidate tokens by probability, accumulate until reaching P, then truncate:
• Setting to 0.9 means only sampling from core vocabulary that covers 90% of total probability
• More dynamic than topK: if one word dominates, the pool may have only 1 word; if probabilities are spread, the pool may have dozens
• Setting to 1.0 disables this feature
Range: 0.00-1.00, Default: 0.95
Min P--min-pRelative probability threshold truncation (modern sampling method recommended by llama.cpp). Sets a floor relative to the most probable Token:
• If the most likely word has 50% probability and minP is 0.1, the threshold = 50% × 0.1 = 5%. Tokens below 5% are discarded
• Perfectly balances high-confidence (fewer choices) and low-confidence (more choices) scenarios, often replacing topP
Range: 0.00-1.00, Default: 0.05
Repeat Penalty--repeat-penaltyDirectly discounts the probability of already-appeared Tokens:
• 1.0 is neutral (no penalty, no encouragement)
• 1.1-1.2 effectively prevents the model from repeating the same sentence like a broken record
• Too high (1.5+) causes the model to force rare words to avoid repetition, resulting in fragmented language
Range: 0.10-2.00, Default: 1.00
Repeat Last N--repeat-last-nDetermines how many Tokens backward the repeat penalty looks:
• 64 means only penalize repetitions within the last 64 tokens
• -1 means look back across the entire current context length
• 0 disables this feature
Options: 0/16/32/64/128/256/512/1024/-1, Default: 64
Presence Penalty--presence-penaltyApplies a fixed penalty to any token that has appeared in the context (regardless of frequency):
• Primarily encourages the model to switch topics and avoid dwelling on the same content
• Positive values encourage new topics; negative values encourage focusing on current topics
Range: -2.00-2.00, Default: 0.00
Frequency Penalty--frequency-penaltyApplies a penalty proportional to how many times a token has appeared in the context:
• The more often a word appears, the heavier the penalty
• Mainly suppresses overused common words (e.g., "then", "so"), making vocabulary more diverse
Range: -2.00-2.00, Default: 0.00

These parameters determine how the engine utilizes CPU, memory, and GPU, having a major impact on inference performance (Tokens/s).

Speculative Decoding Parameters

Speculative Decoding (a.k.a. predictive inference) uses a Draft model to predict multiple subsequent tokens ahead of time, which the main model then validates in one pass, reducing inference steps and significantly improving generation speed. The "Speculative Decoding" setting in the launch configuration supports the following acceleration types:

TypeDescriptionDraft Model Requirement
OffSpeculative decoding disabled; standard token-by-token decoding—
MTP (Multi-Token Prediction)Multi-token prediction acceleration using the model's MTP capability for draftingNo extra file needed when the main model file has built-in MTP layers; otherwise auto-detects the draft model in the mtp/ subdirectory (see "MTP Draft Model File Naming Convention" above)
DFlashDFlash draft model prediction accelerationMust manually specify a separate draft model file
DSparkDSpark draft model prediction accelerationMust manually specify a separate draft model file

After selecting a type, the following parameters can be configured:

UI ConfigurationUnderlying ParameterDetailed Description
Type--spec-typeSelects the speculative decoding type (MTP / DFlash / DSpark). The LLAMACPP launch mode maps to --spec-type draft-<type>; the IK_LLAMACPP launch mode uses the inline syntax --spec-type <type>:n_max=N,n_min=N,p_min=P.
n-max--spec-draft-n-maxNumber of tokens drafted per step, Range: ≥1, Default: 3. Larger values validate more tokens per step for better acceleration, but increase the cost of rollback when validation fails.
n-min--spec-draft-n-minMinimum number of draft tokens: the draft model always generates at least this many tokens per step, so the p-min early stop does not kick in before this count, Range: ≥0 and ≤ n-max, Default: 0. Raising it keeps a minimum of draft tokens validated per step even when the draft confidence drops early.
p-min--spec-draft-p-minMinimum acceptance probability, Range: 0.00-1.00, Default: 0.00. Controls the acceptance threshold for Draft tokens, balancing acceleration and output quality.
draft-ngl--gpu-layers-draftNumber of the draft model's layers offloaded to the GPU. The LLAMACPP launch mode supports a number, auto or all (Default: auto); the IK_LLAMACPP launch mode supports a number only. More GPU layers speed up draft prediction and reduce the latency of rollback when validation fails.
Draft Model--model-draftPath to the draft model file. This setting appears when DFlash / DSpark is selected; startup is rejected if the file does not exist. The MTP type needs no manual specification — it takes effect directly when the main model file has built-in MTP layers; otherwise the system auto-detects the draft model in the mtp/ subdirectory.
Framework Syntax Differences: In the LLAMACPP launch mode, parameters are passed as --spec-type draft-<type> --spec-draft-n-max N --spec-draft-n-min N --spec-draft-p-min P --gpu-layers-draft <layers> --model-draft <path>; in the IK_LLAMACPP launch mode, n_max / n_min / p_min only support the inline syntax --spec-type <type>:n_max=N,n_min=N,p_min=P (the draft model is specified via --model-draft, and the draft model's GPU layer count via --gpu-layers-draft).
Note: DFlash / DSpark types require a draft model file; the system will refuse to start if the file does not exist. For the MTP type, if the main model file has no built-in MTP layers and no draft model is found in the mtp/ subdirectory either, no draft model is loaded and model startup is unaffected.

3. Cache & State Parameters

These parameters control memory usage and session state management.

UI ConfigurationUnderlying ParameterDetailed Description
Cache Size--cache-ramLimit or pre-allocate KV Cache capacity (unit: MiB). Longer context consumes more KV Cache. For massive MoE models, long text causes significant cache inflation. This parameter prevents memory overflow.
KV Cache Quantization-ctk / -ctvSet KV cache quantization type (e.g., f16, q8_0, q4_0). Quantizing KV Cache significantly reduces memory usage but may slightly affect inference accuracy. Recommended q8_0 or q4_0 when VRAM is limited.
Checkpoint Step--checkpoint-min-stepMinimum interval step for context checkpoints. Checkpoints persist session state by saving KV Cache to disk, allowing direct loading next time without re-inference. This parameter controls checkpoint creation frequency.
Checkpoint Count--ctx-checkpointsMaximum number of checkpoints per slot. Works with checkpoint step to manage the number of state files generated, preventing disk space from being filled with checkpoint files.

Main GPU Note: After setting the main GPU, the system moves it to the first position of CUDA_VISIBLE_DEVICES so llama.cpp naturally uses it as the primary card (logical device 0), with no extra -mg parameter needed.
Tensor Split: VRAM allocation then maps to physical GPUs in this reordered order, requiring no manual adjustment and avoiding misaligned VRAM allocation.

GPU Monitoring

Built-in GPU monitoring panel, syncing data every 10 seconds, recording trend charts of the last 60 samples.

Monitoring data is based on real-time parsing of nvidia-smi, allowing intuitive viewing of each GPU's type and VRAM usage.
macOS Does Not Support GPU Monitoring: GPU monitoring depends on the nvidia-smi tool, which is only applicable to NVIDIA GPUs. macOS uses Apple Silicon (M series) or integrated graphics, which do not provide independent GPU monitoring interfaces similar to NVIDIA, so GPU monitoring panels are not available on macOS.

Memory Monitoring

The memory monitoring panel displays system memory usage:

  • Overview CardsDisplays total memory, used memory, available memory, and overall usage percentage in real-time.
  • Trend ChartDraws memory usage fluctuation curves for the past 3 minutes, helping analyze memory peaks during model loading.
  • Status Progress BarVisually presents current memory usage in the form of a progress bar.

Scheduled Restart Management

Compatibility Notice: The scheduled shutdown/restart feature depends on the underlying OS instruction set and hardware support; not all machine models can operate normally. Current test system status: Dual X99 (Ubuntu 22.04, E5-2696 v4) and Mac M1 Pro shutdown/restart work normally; Windows 10 64-bit (z690 motherboard, i7-13700K) shutdown works normally, but automatic wake-up restart is limited by motherboard BIOS and cannot wake up in self-tests.
macOS Restart Special Notice: When macOS executes a scheduled restart, the power adapter must be connected. Without a power connection, the system may refuse to execute the restart or fail to wake up properly after restart; ensure the device is in a powered state.

To reduce energy consumption and maintain system stability, flexible scheduled power on/off solutions are provided.

Task Scheduling & Warning

Supports two task modes:

ModeFeaturesApplicable Scenarios
One-time TaskAutomatically deleted after one executionTemporary maintenance, single experiment
Recurring TaskWorkdays can be specified; automatically calculates the next cycle upon expirationDaily scheduled shutdown/wake

Task Management: Administrators can view all created tasks, including execution time, status (pending/running/expired), and real-time countdown. Supports deleting or postponing tasks (Postpone).

Warning Mechanism: When a task is less than 10 minutes from execution time, the system will pop up a countdown warning card at the top of the page.
